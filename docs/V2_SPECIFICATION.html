Phase 1 — Internal Reasoning

The Reasoning Engine (Claude Opus) performs conceptual decomposition of the user's query. Rather than generating a flat text response, it produces a structured reasoning artifact containing: conceptual primitives (atomic knowledge units), prerequisite dependencies (what must be understood first), a complexity gradient (ordering from simple to complex), and anticipated follow-up vectors (questions the user is likely to ask next).

Phase 2 — Information Classification

The Classifier takes the reasoning output and categorizes every piece of information into a discrete epistemic type. This classification is critical because different data types demand different visual representations, different narration styles, and different positions within the knowledge graph.

Data Type Description Visual Representation KG Node Color
CONCEPT Core idea or abstraction (e.g., "Pod", "Service") Filled rectangle with icon Cyan (#00e5ff)
RELATIONSHIP How concepts connect (e.g., "routes traffic to") Labeled directed edge Edge: Magenta (#ff2d7b)
EXAMPLE Concrete instance (e.g., "nginx pod on 10.244.1.5") Dashed-border card with code Emerald (#00e676)
ANALOGY Familiar comparison (e.g., "Service is like a phone book") Split-panel comparison Amber (#ffab00)
DEFINITION Formal specification (e.g., "ClusterIP: virtual IP") Highlighted text block Violet (#b388ff)
PROCESS Sequential steps (e.g., "DNS → iptables → Pod") Animated flow sequence Cyan gradient
RESOURCE External reference (link, doc, paper) Citation card with link Emerald dim
COUNTERPOINT Common misconception or alternative view Warning-styled callout Magenta dim

Phase 3 — Asynchronous Graph Construction

The Knowledge Graph Builder constructs the graph in concentric depth layers. Depth 0 (the root topic) and Depth 1 (immediate sub-concepts) are built synchronously before the presentation begins. Deeper layers (depth 2+) are expanded asynchronously in the background while the agent is already presenting. This ensures the presentation starts immediately while anticipating potential deep-dives.

OVERFLOW PREVENTION — BOUNDED ASYNCHRONOUS EXPANSION

The async graph builder is constrained by three hard limits: max 50 nodes total per session, max depth 4 from root, and RL-prioritized expansion (only expand nodes the RL agent predicts the user is likely to explore). This prevents combinatorial explosion of nested scenarios while maintaining sufficient anticipatory depth for natural interruptions.

Phase 4 — Presentation Planning

The Presentation Planner receives the knowledge graph and the RL agent's recommended traversal policy, then generates a scene sequence — an ordered list of visual+narration pairs that walk the user through the graph. Each scene focuses on 1-3 nodes and their connecting edges. The planner also pre-computes branch entry points — moments where the user might naturally want to go deeper.

The graph is live, mutable, and traversable — not a static data structure but an evolving representation of the teaching session.

WHY BOUNDED EXPANSION MATTERS

Without bounds, "Kubernetes Networking" could expand into hundreds of nested scenarios: every Service type, every CNI plugin, every kernel networking concept, every cloud provider variation. The RL agent predicts which 2-3 branches the specific user is most likely to explore, and only pre-expands those. If the user asks an unexpected question, the graph mutates on-demand.

Voice-Visual Synchronization

The narration text is sent to the TTS engine which returns word-level timestamps. These timestamps are used to trigger visual events on the canvas — element reveals, highlights, arrow animations, and scene transitions — precisely synchronized with the spoken word. When the agent says "...the Service routes traffic to the Pod...", the arrow between Service and Pod animates at exactly that moment.

Intent Classification on User Speech

While the agent is presenting, the input microphone remains active. Every utterance from the user is classified into one of four intent categories, each triggering a different agent behavior:

IntentSignal ExamplesAgent Behavior
QUESTION "What about NodePort?", "How does DNS work here?" Trigger interrupt protocol (§6)
ACKNOWLEDGMENT "OK", "Got it", "Makes sense", "Hmm" Continue presentation, log as +reward
CONFUSION "Wait what?", "I don't get it", "Can you repeat?" Rephrase current node with alternate analogy/example
COMMAND "Go back", "Skip this", "Show the graph" Execute navigation command

SEAMLESS RESUMPTION

When resuming, the agent doesn't awkwardly restart the scene. It uses a bridging phrase ("So, as we were saying..." / "Coming back to...") and resumes narration from the exact word offset. The newly added graph nodes from the interrupt remain visible but dimmed, maintaining spatial context of what was just explored.

State Encoding

The Learner State Encoder constructs a feature vector from multiple signal sources. This is not a simple profile — it's a real-time, continuously updated representation of the user's current cognitive state within the session: 

interface LearnerState {
  // Real-time session signals
  avgTimePerNode:        number;   // seconds spent per KG node
  interruptRate:          number;   // questions per minute
  confusionRate:          number;   // confusion signals per 5 nodes
  acknowledgmentRate:     number;   // "got it" signals per node
  silenceDuration:        number;   // avg silence after explanations
  revisitCount:           number;   // times user returned to a node
  currentDepth:           number;   // depth in knowledge graph

  // Persistent user profile (cross-session)
  expertiseLevel:         number;   // 0-1 inferred skill
  preferredModality:      string;   // "visual" | "verbal" | "example"
  vocabularyComplexity:   number;   // 0-1 technical vs layman
  optimalPace:            number;   // words per minute preference
  analogyEffectiveness:   number;   // 0-1 how well analogies work
  exampleEffectiveness:   number;   // 0-1 how well examples work
}

Policy Decisions in Practice

The RL agent's policy manifests as concrete presentation decisions. Here are examples of how it adapts for two contrasting learner profiles:

👨‍💻 Experienced Developer

Observed: Low confusion rate, asks deep questions, skips analogies, fast pace

RL Policy: Definition-first strategy, skip analogies, pre-expand deep technical branches (iptables, eBPF), increase pace to 180 WPM, minimal comprehension checks

🎓 Junior Learning K8s

Observed: High confusion rate, needs revisits, responds well to analogies, slower pace

RL Policy: Analogy-first strategy, expand example branches, slow pace to 120 WPM, frequent comprehension checks, visual density: low (2 elements per scene)

CROSS-SESSION LEARNING

The user profile persists across sessions. If the RL agent learned that this user absorbs Process-type data best through animated flows rather than code blocks, that preference carries forward to the next teaching session on a completely different topic.

Dual-View Layout

The client interface presents two synchronized views. The primary canvas (left, ~70% width) shows the focused presentation view — the current scene with 1-3 nodes and their visual representations, animated and narration-synced. The minimap (top-right corner) shows the full knowledge graph with a highlighted viewport indicator showing where the current focus is within the larger graph. Users can click nodes in the minimap to jump, or the agent navigates automatically.

// ── Data Type Classification ─────────────────────
enum DataType {
  CONCEPT      = 'CONCEPT',
  RELATIONSHIP = 'RELATIONSHIP',
  EXAMPLE      = 'EXAMPLE',
  ANALOGY      = 'ANALOGY',
  DEFINITION   = 'DEFINITION',
  PROCESS      = 'PROCESS',
  RESOURCE     = 'RESOURCE',
  COUNTERPOINT = 'COUNTERPOINT',
}

enum EdgeType {
  REQUIRES     = 'REQUIRES',      // prerequisite dependency
  CONTAINS     = 'CONTAINS',      // part-of relationship
  RELATES_TO   = 'RELATES_TO',    // general association
  EXEMPLIFIES  = 'EXEMPLIFIES',   // concrete instance of
  CONTRADICTS  = 'CONTRADICTS',   // counterpoint / misconception
  LEADS_TO     = 'LEADS_TO',      // causal or sequential
  DEEPENS      = 'DEEPENS',       // more detailed view of
}

// ── Knowledge Graph Node ─────────────────────────
interface KGNode {
  id:               string;
  label:            string;
  type:             DataType;
  depth:            number;
  content:          string;         // full text content
  narration:        string;         // TTS-optimized text
  visual:           VisualSpec;
  rlRelevanceScore: number;        // 0-1, set by RL agent
  isExpanded:       boolean;        // children generated?
  isPresented:      boolean;        // already narrated?
  parentId:         string | null;
  metadata:         Record<string, any>;
}

// ── Knowledge Graph Edge ─────────────────────────
interface KGEdge {
  id:           string;
  sourceId:     string;
  targetId:     string;
  label:        string;
  type:         EdgeType;
  weight:       number;          // relevance weight
  isPresented: boolean;
}

// ── Full Knowledge Graph ─────────────────────────
interface KnowledgeGraph {
  sessionId:    string;
  rootNodeId:   string;
  nodes:        Map<string, KGNode>;
  edges:        Map<string, KGEdge>;
  maxDepth:     number;
  nodeLimit:    number;          // default: 50
  createdAt:    number;
  updatedAt:    number;
}
